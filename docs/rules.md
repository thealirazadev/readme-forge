# Rules: readme-forge

These rules are binding for anyone (human or agent) working on readme-forge. When a rule and a convenience conflict, the rule wins.

## Conventions

- **Language / version:** Python 3.10+. Do not use syntax that breaks on 3.10.
- **Preferred libraries:** click (CLI), rich (output/preview/progress), anthropic (API), pathspec (`.gitignore`), PyYAML (YAML manifests), tomllib/tomli (TOML), python-dotenv (`.env`), pytest (tests). Do not introduce alternatives to these for the same job.
- **What to avoid:** no argparse (use click); no `print()` for user-facing output (use the renderer / rich console); no `requests`/`httpx` for the model call (use the `anthropic` SDK); no global mutable singletons; no heavy frameworks; no async unless a concrete need appears.
- **Naming:** PEP 8. snake_case modules and functions, PascalCase classes, UPPER_SNAKE constants. Module names are snake_case (`scanner.py`, `logging_setup.py`).
- **Type hints:** required on public functions and dataclasses.
- **Commit format:** Conventional Commits with a short imperative subject, for example `feat: add gitignore-aware scanner`, `fix: map 401 to friendly invalid-key error`, `test: cover empty-repo summary`. Subject <= 72 chars, imperative mood, no trailing period.
- **ONE COMMIT PER FEATURE/TASK.** Never batch multiple features into one commit. Each commit builds and passes tests on its own.
- **Pin exact dependency versions** in `pyproject.toml` (use `==`, not ranges) and **commit the lockfile** (`requirements.lock` or equivalent) so builds are reproducible. Do not bump versions casually.

## Error handling and logging

- Define a small set of exception types in `errors.py` (for example `NotARepoError`, `EmptyRepoError`, `ApiError` with subtypes for network / rate limit / invalid key, `OverwriteRefused`). Each maps to a friendly message and an exit code.
- **Handle these cases explicitly:**
  - **Non-repo / non-directory path:** friendly message ("path is not a directory: ..."), exit code 2.
  - **Unreadable files:** skip the file, add a note to the summary, continue. Never abort the whole scan for one bad file.
  - **Empty repo / no code files:** friendly message or a clearly-empty summary; do not call the API with nothing meaningful unless the user proceeds. Exit cleanly.
  - **Model API errors:** network failure, rate limit (429), invalid key (401), and other HTTP errors each get a distinct friendly message and exit code 3.
- **Friendly CLI errors vs detailed logs:** by default show a one-line, human-readable error to stderr. With `--verbose`, additionally show the underlying detail (status codes, request ids, stack context). **Never dump raw tracebacks by default.** A traceback appears only under `--verbose`.
- **One consistent error style:** all user-facing errors go through the same formatter (a red "Error:" prefix when color is on, plain "Error:" otherwise), one line, actionable where possible ("set ANTHROPIC_API_KEY or add it to .env").
- Logging uses the stdlib `logging` module configured in `logging_setup.py`: WARNING baseline, ERROR-only under `--quiet`, DEBUG under `--verbose`. User-facing output is separate from logs and goes through the renderer.

## Security

- **Never hardcode the API key.** Read it from the environment or `.env` only. No default, no fallback literal, no committed key.
- **Never log the key**, not even partially, at any log level. Redact it if it could appear in an error object.
- **Respect `.gitignore`** during the scan and skip anything it matches. Also apply a built-in ignore list (`.git`, `node_modules`, `venv`, `.venv`, `dist`, `build`, `__pycache__`, etc.).
- **Skip secrets and large binaries.** Never read files matching a secret denylist (`.env`, `.env.*`, `*.pem`, `*.key`, `id_rsa`, `*.p12`, `credentials`, `secrets.*`) or files above the size threshold. These are never read and never sent to the API.
- **Document what is sent to the API** (see architecture.md): only the bounded `RepoSummary` and requested sections. Only recognized manifest file contents are read; other file bodies are never sent.
- No telemetry, no analytics, no phone-home other than the explicit Claude API call.

## Simplicity (YAGNI / KISS)

- Build only what the current phase needs. No speculative abstraction, no plugin systems, no config for things nobody asked for.
- Prefer a function to a class, a dataclass to a framework, stdlib to a dependency, one file to many.
- If a feature is not in the current phase, it goes to the backlog, not into the code.

## Code style

- Comments are sparse and explain **why**, not **what**. No commented-out code.
- Docstrings are concise: one line for simple functions, a short paragraph for modules and non-obvious functions.
- **No emoji anywhere** in code, output, comments, or docs.
- **No authorship attribution anywhere** — never write "generated by", "co-authored by", or that an assistant wrote the code, in source, commits, or docs.
- Conventional Commits (see above). Run Ruff and Black before committing; the tree must be clean.

## Boundaries

- **Never overwrite an existing README** without an explicit `--overwrite` flag or an interactive confirmation. Default behavior with an existing file and no flag is to ask; declining writes nothing.
- **No wholesale delete or rewrite** of files the tool did not create. The tool writes exactly one file (the target README) and only after the write gate.
- **Never change PRD.md or architecture.md** as a side effect. If the work reveals they are wrong, stop and flag it; do not silently edit them.
- **No new dependency without approval.** Adding anything beyond the libraries listed in Conventions requires explicit sign-off, then a pinned version and lockfile update.
- **Ask when ambiguous.** If requirements are unclear, stop and ask rather than guessing.
- **Stop after 2 failed fix attempts** on the same problem and report what was tried and what is blocking, instead of thrashing.
- **Scope every change.** Label it as: current phase, a new phase, or backlog. Do not pull backlog work into the current phase without saying so.
